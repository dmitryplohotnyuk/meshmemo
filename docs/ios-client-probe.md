# Проверка iOS 2.7.22 (2395) без радио

Статус: **проверка на iPhone завершена; дедупликация FAIL**.
Версия приложения: iOS 2.7.22 (2395), подтверждена пользователем.

Команда `ios-probe` имитирует отдельную Meshtastic-ноду через TCP и выдаёт
только синтетические сообщения. Она не открывает COM-порт, не шифрует и не
передаёт пакеты в эфир, не изменяет прошивку. Это диагностический инструмент,
не реализация S&F-сервера и не замена аппаратной приёмки.

## Перед подключением

Сохраните резервную копию данных текущей ноды в iOS-приложении и убедитесь,
что она доступна для восстановления. Лучше использовать отдельный тестовый
профиль/устройство, если это возможно. В проверенных исходниках iOS обработчик
MyInfo вызывает проверку чужой базы, а подключение другой ноды меняет активное
хранилище. Нельзя обещать, что эксперимент оставит текущую историю на экране.
[Исходный обработчик](https://github.com/meshtastic/Meshtastic-Apple/blob/6f3ee55bc7c9ff9b2d6f0c64b23de05ddeeaae21/Meshtastic/Accessory/Accessory%20Manager/AccessoryManager%2BFromRadio.swift#L193-L212).
Это конкретный риск переключения ноды, а не требование перепрошивать устройство.

Сервис по умолчанию слушает только localhost. Для iPhone нужен конкретный
приватный IPv4 адрес этого ПК и общая локальная сеть. Публичные адреса и wildcard
bind запрещены. Автоматические правила firewall скрипт не создаёт.

## Запуск и сценарий

Из корня проекта, после установки пакета:

```powershell
.venv/Scripts/python.exe -m pip install -e . --no-deps --no-build-isolation
.venv/Scripts/meshtastic-sf-server.exe ios-probe --bind <LAN-IP-этого-ПК> --port 4403
```

1. На iPhone используйте штатное TCP-подключение к указанному адресу и порту.
   Должна появиться тестовая нода **LOCAL TEST - NO RADIO**, канал **SFTEST**
   и автор **Synthetic SF author**. Никакие реальные ключи вводить не нужно.
2. Дождитесь появления канала. В терминале вводите названия шагов из таблицы
   по одному. После каждого шага дождитесь обновления сообщений в iOS и
   запишите число сообщений с текущим `SFTEST-xxxxxxxx` из терминала.
3. `quit` прерывает тест. После последнего шага Enter закрывает подключение.
   Затем вернитесь к своей ноде и проверьте восстановление её истории.

| Команда | Входящие данные | Ожидаемое число сообщений этой категории |
| --- | --- | --- |
| `baseline` | Обычный channel text BASELINE | BASELINE = 1 |
| `live` | Обычный channel text LIVE с ID X | LIVE = 1 |
| `replay` | S&F broadcast replay LIVE: новый outer ID, original_id=X | LIVE = 1 |
| `replay-again` | Ещё один replay LIVE с другим outer ID, original_id=X | LIVE = 1 |
| `offline` | S&F OFFLINE с original_id=Y, оригинал не подавался | OFFLINE = 1 |
| `offline-again` | Повтор OFFLINE с другим outer ID, original_id=Y | OFFLINE = 1 |

Все S&F тексты имеют rr=9 / port=65, исходного автора и unicast destination
тестовой ноды. Приложение должно восстановить channel chat. Все внешние ID
различны; исходные ID LIVE и OFFLINE различны. Текст содержит `Привіт Ґґ`.
Повторный запуск создаёт новую метку, синтетические ID и идентичность ноды;
не запускайте его многократно без необходимости переключать базу.

Если BASELINE не виден, остальные результаты неинтерпретируемы: нужно исправить
TCP-handshake/совместимость тестовой ноды, а не делать вывод о replay. Если LIVE
или OFFLINE не видны вообще, это тоже не успешная дедупликация. Если LIVE=3 и
OFFLINE=2, приложение, вероятно, использует внешние ID; это FAIL сценария.

## Что уже проверено автоматически

Framing с фрагментированным TCP-потоком, protobuf payload, original_id,
уникальность внешних ID, одинаковые исходные тексты и ограничения bind.
Немодифицированный официальный Python TCPInterface 2.7.11 успешно проходит
handshake на loopback. Это **не доказывает** совместимость handshake с iOS.
Клиентские записи и координаты инструмент отбрасывает и не сохраняет.

После теста достаточно сообщить шесть наблюдаемых чисел, имя канала и автора.
Не присылайте реальные ключи, экспорт базы или приватные сообщения.

| Поле результата | Значение |
| --- | --- |
| iOS app | 2.7.22 (2395), указано пользователем |
| BASELINE | 1, текст/канал/автор подтверждены пользователем |
| LIVE после live / replay / replay-again | 1 / **2 (FAIL)** / **3 (FAIL)**, подтверждено пользователем |
| OFFLINE после offline / offline-again | 1 / **2 (FAIL)**, подтверждено пользователем |
| Канал и автор | SFTEST / Synthetic SF author, подтверждено скриншотом |
| Radio/multi-hop | НЕ ПРОВЕРЯЕТСЯ этим тестом |

Первое наблюдение 2026-09-25: на присланном пользователем скриншоте видны
одно BASELINE и два одинаковых LIVE с меткой SFTEST-07c7e79d. Второй LIVE
появился после S&F replay с новым внешним ID и original_id исходного LIVE.
Таким образом, требование live/replay deduplication в этом сценарии не выполнено
непосредственно на целевой версии приложения. Это наблюдение не устанавливает
точный commit бинарника и не является проверкой радио-доставки. Скриншот
в публичные файлы репозитория не копируется.

Итог: пользователь подтвердил LIVE=3 после повторного replay, затем OFFLINE=1
после первой выдачи и OFFLINE=2 после повторной. Приём ранее не полученного
сообщения, канал и автор работают; оба сценария дедупликации не выполнены.
Тестовый TCP-сервис остановлен после последнего наблюдения. Прошивка и радио
не затрагивались; восстановление/возврат к базе реальной ноды пользователь
проверяет отдельно. Машиночитаемый итог: [ios-client-probe-result.json](ios-client-probe-result.json).
