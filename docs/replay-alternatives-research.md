# Replay с iOS из App Store: исследование альтернатив

Проверено 2026-09-25. Цель: Linux + патч только серверной USB-ноды,
неизменённые клиентские/промежуточные ноды, официальный iOS 2.7.22 (2395),
исходный автор и канал, шифрование и отсутствие дублей. TestFlight и собственная
iOS-сборка исключены решением пользователя. Это исследование, не смена ТЗ.

## Вывод

Готового решения, подтверждённо выполняющего все эти условия, не найдено.
Найден конкретный upstream-путь исправления: поддержка `StoreAndForward.original_id`
в официальном Apple-клиенте. Android уже получил аналогичное исправление.
В проверенной Apple main оно отсутствует; даты выхода такого исправления в
App Store нет. Отрицательный поиск PR не доказывает, что никто над ним не работает.

Точный повтор исходного шифротекста остаётся кандидатом для узкого эксперимента
с ранее выключенной принимающей нодой. Он не обеспечивает общую выдачу истории
через произвольные штатные ретрансляторы и не равен ответу S&F v1.
REPLAY в нашем диагностическом патче остаётся выключен.

## Найденное upstream-исправление

- [protobufs #1080](https://github.com/meshtastic/protobufs/pull/1080), merged
  2026-09-13: поле исходного ID в S&F payload.
- [firmware #11849](https://github.com/meshtastic/firmware/pull/11849), merged
  2026-09-16: новый внешний ID при отправке истории по радио; прежний ID
  переносится в payload. При локальной выдаче в PhoneAPI ID остаётся исходным.
- [Android #7158](https://github.com/meshtastic/Meshtastic-Android/pull/7158), merged
  2026-09-14: обработчик текста использует `original_id`, если он ненулевой,
  иначе сохраняет прежнее поведение. Автор PR отдельно отмечает Apple-путь
  как требующий проверки. Это независимое подтверждение механизма наших дублей.

Наша [проверка реального iPhone](ios-client-probe.md) сильнее предположения по
исходникам: LIVE дал 1→2→3 сообщения, OFFLINE — 1→2 при повторной выдаче.
Автор, канал и UTF-8 сохранялись. Тест шёл через TCP, радио не участвовало.

Проверенная Apple main `6f3ee55bc7c9ff9b2d6f0c64b23de05ddeeaae21` передаёт
S&F-пакет в обработчик текста без замены ID. Проверка существующей записи и
создание новой используют внешний `packet.id`:
[MeshPackets.swift](https://github.com/meshtastic/Meshtastic-Apple/blob/6f3ee55bc7c9ff9b2d6f0c64b23de05ddeeaae21/Meshtastic/Helpers/MeshPackets.swift#L1856),
[AccessoryManager+FromRadio.swift](https://github.com/meshtastic/Meshtastic-Apple/blob/6f3ee55bc7c9ff9b2d6f0c64b23de05ddeeaae21/Meshtastic/Accessory/Accessory%20Manager/AccessoryManager%2BFromRadio.swift#L621).
Main нельзя приравнивать к исходникам App Store build 2395: точная привязка
этой сборки к commit неизвестна, её поведение подтверждено прямым тестом.

## Может ли помочь обычное обновление прошивки принимающей ноды?

Проверены установленная stable `54e0d8d`, последний опубликованный alpha
`v2.8.0.47db0e3` и develop `f90b48ea6cda35b5f6fdd4cd659498d28d8bd153`.
В их `StoreForwardModule::handleReceivedProtobuf` нет преобразования входящего
S&F текста с `original_id` в пакет с исходным ID перед передачей телефону.
Необработанный текст проходит дальше в обычную доставку телефону.

В develop действительно есть ветка `preparePayload(..., local=true)`, которая
выдаёт оригинальный ID как обычный текст. Но это выдача **собственного локального
архива ноды через PhoneAPI**, а не распаковка полученного по LoRa replay.
Поэтому она не исправляет наш сценарий с удалённым Linux-сервером.

Источники: [stable](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/modules/StoreForwardModule.cpp),
[alpha](https://github.com/meshtastic/firmware/blob/v2.8.0.47db0e3/src/modules/StoreForwardModule.cpp),
[develop](https://github.com/meshtastic/firmware/blob/f90b48ea6cda35b5f6fdd4cd659498d28d8bd153/src/modules/StoreForwardModule.cpp).
Обновление этих прошивок само по себе не является найденным решением.

## Сравнение обходных путей

| Вариант | Что даёт | Почему не закрывает исходное ТЗ |
| --- | --- | --- |
| Свежий внешний ID + `original_id` | Отдельная идентичность передачи и сообщения | Целевой iOS не использует исходный ID для дедупликации; подтверждено тестом |
| Старый внешний ID + S&F-обёртка | Потенциально совпадающий ID в iOS | Меняет plaintext при прежних sender/ID/key, повторяя AES-CTR nonce; также остаются сетевые кэши |
| Побайтовый повтор исходного ciphertext, broadcast | Сохраняет исходные sender/ID/канал без повторного шифрования изменённых данных | Сетевые кэши могут остановить доставку; обычный текст вместо S&F-ответа; история рассылается всему каналу |
| Тот же ciphertext как unicast | Адресная доставка без новой S&F-обёртки | Штатный PKI-capable Router отклоняет channel-encrypted TEXT, адресованный себе, как legacy DM |
| Постоянный новый ID на каждое архивное сообщение | Может убрать повторные копии самой истории в UI | LIVE всё равно имеет другой ID; остаются два сообщения. Радиокэш мешает повторной доставке |
| Сервер запоминает, кому уже выдавал запись | Снижает повторные отправки | Не знает, что iPhone получил напрямую и что сохранилось в его БД; отправка не равна доставке |
| TCP-прокси нормализует ID перед iOS | Возможная совместимость App Store без патча приложения | Телефон должен получать пакеты через этот IP-прокси. При BLE-подключении к удалённой ноде сервер не находится на пути её PhoneAPI |
| Патч принимающей ноды нормализует ID после расшифровки | Принципиально позволяет оставить App Store-клиент | Нарушает условие «патч только серверной ноды»; не предлагается как согласованное изменение |
| S&F++ | Отдельный протокол синхронизации истории | Проверенный прототип native Linux; PR не merged, готового пути для нашей клиентской сети нет |
| Готовый MeshMonitor | Хранение/просмотр и приём S&F в другом клиенте | Его документация описывает S&F client, сервер остаётся на ноде; это не исправление Apple-дедупликации |

PKI от имени сервера меняет видимого автора; PKI от имени оригинального автора
потребовал бы его закрытый ключ. Отдельный ключ/канал истории не устраняет
фильтрацию по исходному sender/ID и меняет требования к настройке/каналу.
`reply_id` связывает сообщения как ответы, а не задаёт идентичность сообщения
в проверенном Apple-обработчике. Эти варианты не дают общего обхода.

Источники для шифрования и legacy DM:
[разбор nonce](replay-security.md),
[Router stable](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/Router.cpp),
[Router develop](https://github.com/meshtastic/firmware/blob/f90b48ea6cda35b5f6fdd4cd659498d28d8bd153/src/mesh/Router.cpp).

## Почему точный повтор ciphertext не гарантирует восстановление

Это не проблема нового шифрования: повторяется уже существующий ciphertext.
Нужно сохранять именно исходные bytes зашифрованного `Data`, его sender/ID,
channel/key scope и значимые поля заголовка. Повторная сериализация текста или
decoded SDK packet не доказывает побайтовую идентичность. Такой захват в нашем
диагностическом USB-патче пока не реализован.

Однако `PacketHistory::find` в stable и проверенном develop ищет sender+ID
без срока давности. Записи вытесняются при наполнении кэша. Константа
`RECENT_WARN_AGE = 10 min` относится к диагностике вытеснения, а не к TTL:
ожидание 10 минут или суток само по себе не гарантирует пропуск.

`NextHopRouter` и `FloodingRouter` допускают некоторые повторные ретрансляции:
повтор от источника, увеличение hop limit, fallback. Поэтому утверждение
«любой дубль всегда отбрасывается на первом ретрансляторе» неверно. Но эти ветки
не дают гарантии восстановления истории: обработчик возвращает filtered,
а `reprocessPacket` не повторяет обычную доставку текста в телефон.

Контрпример по коду: нода услышала исходный пакет, пока телефон был отключён.
ID всё ещё в её кэше. Повтор может быть ретранслирован/подтверждён, но сам текст
не обязан снова попасть в PhoneAPI. В цепочке ретрансляторов следующий узел с
тем же ID может отсечь повтор, когда `hop_start != hop_limit` и нет upgrade/fallback.
Увеличение hop limit не даёт неограниченного числа восстановлений.

Источники:
[PacketHistory stable](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/PacketHistory.cpp),
[PacketHistory develop](https://github.com/meshtastic/firmware/blob/f90b48ea6cda35b5f6fdd4cd659498d28d8bd153/src/mesh/PacketHistory.cpp),
[NextHopRouter stable](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/NextHopRouter.cpp),
[FloodingRouter stable](https://github.com/meshtastic/firmware/blob/54e0d8d0ab2ff56b3a9ce967e53f79e49af560fb/src/mesh/FloodingRouter.cpp).
Это вывод из исходников; новые радиоэксперименты не проводились.

Узкий эксперимент имел бы смысл только при явно ограниченной задаче:
принимающая нода сама не слышала оригинал, есть прямой радиолинк, проверяется
обычный текст с прежним ID. Нужны отдельные проверки iOS-дедупликации, реально
исходных ciphertext bytes и поведения после переподключения. Успех не закрывает
multi-hop и восстановление после отключения одного телефона.

## S&F++ и готовые проекты

[Firmware PR #9041](https://github.com/meshtastic/firmware/pull/9041) закрыт
2026-09-19, `merged_at = null`. Автор ограничивает прототип native Linux:
Linux-ноды синхронизируют цепочку сообщений на primary channel.
В дереве проверенного firmware develop нет модуля S&F++.
Наличие зарезервированного port 35 в protobuf не означает готовую поддержку
на клиентской ноде или в iOS.

[Документация MeshMonitor](https://meshmonitor.org/features/store-forward)
описывает приём S&F и пометки истории, оставляя серверную функцию на ноде.
На странице есть противоречие относительно ручного запроса истории; это
не влияет на вывод: обещания исправить дедупликацию официального iOS там нет.

## Рекомендованный следующий шаг

Для сохранения полного ТЗ наиболее обоснован путь через upstream Apple:
официальный клиент должен применять ненулевой `original_id` в обработке
`ROUTER_TEXT_BROADCAST/DIRECT` до проверки дубля и сохранения записи, с fallback
на внешний ID для старых серверов. Требуются тесты LIVE+replay, повторной выдачи,
первого OFFLINE replay и старого формата без поля. Это направление исправления,
не готовый патч: надо отдельно учитывать текущую схему уникальности messageId
и коллизии ID разных отправителей.

После появления исправления в **App Store** повторить наш синтетический тест,
затем проверять радио, частные каналы и multi-hop. Исправление в main или
TestFlight само по себе условие пользователя не выполняет.

Доказательств для upstream уже достаточно: версия/build, synthetic fixtures,
наблюдаемые количества сообщений и ссылки на соседние PR. Исследование не
включало публикацию issue/PR, отправку сообщений разработчикам или прошивку ноды.
Продолжать независимые части Linux-сервера можно, но успешное хранение в SQLite
не следует выдавать за решённую совместимость replay.
