# Выдача истории по запросу — экспериментальный профиль 1

Реализовано 2026-09-30. Новые установки и базы, впервые получающие настройку
выдачи при миграции, начинают с **выключенной** выдачей. Сохранённый выбор
оператора при обновлении сохраняется; на тестовом сервере выдача включена
оператором. Текущая USB-нода прошита профилем 1/3;
запись, сохранность настроек и 75 секунд USB-связи проверены. Радиорезультаты
ниже получены на предыдущей сборке и не подтверждают новые серверные каналы. Адресные S&F-запросы заблокированы
несовместимостью с PKI (проверка ниже). В 0.1.0a3 добавлен запрос текстовой
командой `/history <hours>` в закрытом канале; он использует прежний планировщик
и ограничения. Команды не архивируются и не попадают в выдачу.
Подробности: [руководство](user-guide.ru.md#выдача-истории-по-радио).

## Аппаратная проверка 2026-09-30: потеря канала в запросе

На Debian проверены USB-приём, сохранение текста Private, запуск через systemd
и повторный запуск после сбоя. Объявления S&F приняты радиочередью серверной ноды;
после повторного объявления пользователь подтвердил появление Client History
в iOS 2.7.22 (2395).

Клиентская NRF52_PROMICRO_DIY с firmware 2.7.15.d18f3f7a6 отправила через USB
один штатный unicast CLIENT_HISTORY (port 65, окно 60 минут) по своему Private,
индекс 2. На серверной ноде этот канал имеет индекс 1. В принятом FromRadio
наблюдались `rr=65`, `pki_encrypted=true`, `channel=0`: прошивка автоматически
выбрала PKI и потеряла привязку к каналу. Сервер отклонил такой запрос согласно
действующему контракту; счётчик принятых запросов остался 0. Клиент получил
маршрутные ответы NONE и NO_RESPONSE. Содержимое переписки и ключи не выводились.

Это отдельный блокер от известной ошибки дедупликации iOS. В проверенном
[Router.cpp upstream develop](https://github.com/meshtastic/firmware/blob/develop/src/mesh/Router.cpp)
port 65 также не исключён из автоматического PKI. Есть
[связанный отчёт upstream #9932](https://github.com/meshtastic/firmware/issues/9932)
о потере канала при S&F/PKI; он не является подтверждением исправления.

Нельзя просто снять запрет PKI или трактовать полученный channel=0 как разрешение
читать первичный/любой приватный канал. Варианты дальнейшей совместимости:

- Явное разрешение оператором: проверенный публичный ключ конкретной ноды и
  конкретный канал/scope на сервере. Тогда штатная кнопка может работать с
  обычной клиентской прошивкой. Один номер ноды недостаточен для такого допуска.
- Запрос внутри приватного канала, с сохранением PSK/scope-проверки; интерфейсом
  запроса будет команда в чате.
- Изменение клиентской прошивки/протокола, сохраняющее канал для S&F-запросов.

Текстовая команда реализована; её радиопроверка описана в конце документа.
Допуск по PKI-ключу к истории отдельного канала не реализован: список
администраторов `/channel add` не даёт права читать историю через Client History. До радиопроверки
совместимость штатной кнопки с этой конфигурацией не заявляется. Также требуется
проверить канал ответов, сообщения от самой серверной ноды и автоматический
NO_RESPONSE прошивки при внешнем обработчике запросов.

## Использование после подготовки оборудования

В админке: **Настройки → Выдача истории по радио → Отвечать на запросы истории**.
Настройка сохраняется в SQLite и применяется без перезапуска. Выключение очищает
очередь и прекращает ответы. Уже переданный прошивке пакет может уйти в эфир.

Требуется USB-прошивка **профиля 1, revision 2 или 3** (для серверных каналов —
**revision 3**), отключённый встроенный Store &
Forward ноды и официальный клиент с поддержкой `original_id`. Проверенное ранее
iOS 2.7.22 (2395) создаёт дубли. Исправление upstream не заменяет проверку
конкретного App Store-релиза.

При включении сервер может объявляться S&F heartbeat в закрытых каналах USB-ноды.
Для каналов, добавленных только на сервере, heartbeat отсутствует.
Объявления выключаются отдельно; период задаётся от 15 до 1440 минут (default 15).
Клиент запрашивает историю командой `/history 6` в нужном закрытом канале.
Штатный unicast `STORE_FORWARD_APP / CLIENT_HISTORY` остаётся поддержанным
для запросов с сохранённым каналом без PKI. При выключении отсутствуют
и heartbeat, и ответы на запросы.

В 0.1.0a7 текстовая команда `/history` больше не отправляет ROUTER_HISTORY со
сводкой Total messages / History window / Last request. Выдаются только тексты;
пустой результат не создаёт очередь и остаётся без ответа, но учитывает cooldown.
Для штатного CLIENT_HISTORY заголовок сохранён, в том числе при пустом результате.
Прошивка и схема базы не меняются.

## Текущий контракт

- Декодированные адресные запросы port 65 либо широковещательные команды
  `/history <hours>` на port 1. Публичные
  каналы/default PSK, MQTT, PKI, собственные и некорректные запросы исключены.
- В админке задаются число сообщений (1–100, default 20), окно по умолчанию
  (1–10080 минут, default 1440) и максимальное окно клиента (1–10080, default 10080).
  В интерфейсе максимальное окно отображается в часах (до 168); API и база
  сохраняют минуты. Значение по умолчанию находится в разделе совместимости
  с Client History и при сохранении ограничивается максимумом. Ответ содержит окно в
  миллисекундах; последние подходящие сообщения выдаются от старых к новым.
- Сохраняется автор. Сообщения requester, конфликтующие/неоднозначные sender/ID
  и тексты длиннее 192 UTF-8 байт для каналов ноды или 160 байт для серверных
  каналов не выдаются, но остаются в архиве. Нет обрезки
  текста или собственной фрагментации.
- Поддержаны stats/ping/abort/error/pong. Stats ограничен каналом запроса.
  Отмена возможна только от активного requester в том же scope.
- Одна выдача; срок не меньше 180 секунд и увеличивается с размером/интервалом
  очереди. Интервал между подачами ноде — 5–60 секунд (default 5);
  control queue ограничена четырьмя элементами. При busy новый клиент получает
  ROUTER_BUSY после текущей выдачи. History requests одного requester/scope —
  раз в 30–3600 секунд (default 60); одинаковый request ID — раз в 120 секунд.
  Кеши ограничены. Изменение настроек выдачи отменяет текущую очередь.
- Запись чатов и выдача переключаются независимо. Retention использует host time.
- Выдача — ограниченный снимок. Клиентский `last_request` не применяется, ответ
  содержит 0; это не курсор доставки. Повторный запрос снова выбирает последние
  подходящие записи, клиент подавляет дубли по `original_id`. Весь большой архив
  автоматически последовательными запросами не выгружается.
- USB disconnect, смена scope, timeout отменяют текущую выдачу; нет возобновления
  старой очереди после reconnect. Счётчик показывает передачу в локальный сервис
  ноды, а не подтверждение получения удалённым телефоном.

## Идентичность и канал

Replay имеет исходного автора, новый внешний MeshPacket.id, port 65, rr=9 и
StoreAndForward.original_id с исходным packet ID. USB-патч вызывает mesh service,
минуя обычную подмену автора в Client API. Reply ID и emoji сохраняются.
Изменённый payload не шифруется намеренно под исходным sender/ID.

Внешний ID резервируется SQLite-транзакцией до USB-команды. Проверяются известные
исходные ID автора и журнал уже зарезервированных ID. Журнал переживает retention
и restart; его предел — миллион записей, после которого выдача останавливается.
Случайный новый ID не даёт гарантии от совпадения с будущим/неизвестным ID автора
в 32-битном пространстве MeshPacket, но устраняет намеренный повтор исходного nonce.

Выборка ограничена HMAC scope текущих ChannelSettings/LoRa. Для каналов USB-ноды команда содержит
16 байт SHA-256 от `LE32(channel_size) || serialized ChannelSettings || serialized
LoRaConfig`. Прошивка проверяет этот digest, приватный ключ канала, airtime и
свободную очередь до подачи пакета. Это проверка согласованности, не отдельная
аутентификация. Ключи не сохраняются в журнале ID и не выдаются API. Для серверных каналов
операция 5 передаёт готовый шифротекст и digest только LoRaConfig. Проверка
ключа и содержимого выполняется хостом, прошивка не может прочитать payload.
Подробности: [серверные каналы](server-channels.md).
Не перенастраивайте радио во время выдачи: уже поданный mesh-пакет нельзя атомарно
связать с последующим изменением настроек ноды.

USB retry повторяет те же session/token/bytes. Firmware кеширует ответ и не
подаёт пакет повторно. При timeout новая сессия не возобновляет неизвестный пакет.
Stock/diagnostic firmware не проходит capability handshake; fallback к обычному
ToRadio.packet отсутствует. Закрытый канал авторизует группу через PSK; отдельной
криптографической аутентификации requester протокол не предоставляет.

## Сборка и проверки

```sh
python scripts/prepare-firmware.py --profile inherited-ua22 --replay
meshtastic-sf-server probe --device COM7 --profile 1
```

Для отдельной сборки укажите `--destination`; существующий checkout не заменяется.
Патчи `0003-usb-replay.patch` и `0004-usb-poll.patch` применяются после
унаследованных изменений и диагностики. Затем применяются `0005-usb-screen-timeout.patch`
и `0006-server-channels.patch`; radio adapter находится в `firmware/replay/`. Сборка не прошивает
ноду. Для native replay tests checkout должен быть подготовлен с `--replay`.

Offline-тесты: выключенный режим без USB-отправок, scope/filter/limits, pacing,
отмена, старый профиль/timeout, журнал ID, web toggle, C++ exact retry. Реальный
C++ encoder проверен независимым Python protobuf decoder, включая кириллицу,
предельный размер и original_id UINT32_MAX.

App-only update выполнен после чтения живой разметки и полного backup flash;
конфигурация сохранена, локальный HELLO проходит со штатным таймаутом.
Перед включением остаются аппаратные проверки
config digest, discovery, secondary private channel, исходного автора,
live/replay и повторного запроса без дублей, multi-hop, очереди и остановки выдачи.

## Проверка текстовой команды 2026-09-30

MeshMemo 0.1.0a3 установлен на Debian. Клиентская NRF52_PROMICRO_DIY со штатной
прошивкой 2.7.15 отправила `/history 6` в Private (индекс 2 на клиенте, 1 на сервере).
Клиент по радио получил SERVER_HISTORY с количеством 1 и ROUTER_TEXT (rr=9)
от исходного автора на своём канале 2, без PKI. Количество записей базы осталось 2;
команда не записалась. Проверены пароль, целостность базы, активный сервис и автозапуск.

Заголовок SERVER_HISTORY пришёл по PKI на channel 0; сам проверенный текст от
другого автора пришёл правильно по PSK в Private. Это не подтверждает выдачу
текстов, автором которых является сама серверная нода: для них остаётся отдельный
риск автоматического PKI. Отображение на iPhone, повторная выдача без дублей и
многопереходная доставка этим тестом не проверены. Порт клиентской ноды закрыт.
